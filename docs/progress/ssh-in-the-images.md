# SSH in the images: the daemon lifecycle, proven on a booted box

- **Status:** done
- **Date:** 2026-09-10
- **Specs touched:** docs/specs/BUILD.md, docs/specs/ENVIRONMENT.md

Closes #467. It finishes what [ssh-per-account-access.md](ssh-per-account-access.md) (#463 / #464) left open: that slice built the whole path from the brain's API down to the rendered sshd config, and said so honestly in its own gaps — no image could run it, and a unit test cannot show a port closing. This one puts SSH into both images and adds the boot test that watches :22 open and close on a real box.

## What was done

**The hosted image carries `openssh-server`, stopped.** `dev/cloud/mkosi.conf` installs it and `dev/cloud/expected-packages.txt` lists it and the sixteen packages it drags in, so the lean exact-match guard still holds. Both files named it as a package that must never appear; `DECISIONS.md` 2026-09-09 reversed that, and the comments now say why.

The daemon does not start at boot. Debian's `openssh-server` postinst enables `ssh.service`, so `dev/cloud/mkosi.postinst.chroot` removes the `multi-user.target.wants` link and adds a preset saying `disable`, so a later `preset-all` cannot put it back. This matters more on hosted than anywhere else: there is no malmo firewall and the provider attaches none, so the daemon's run state is the only thing that closes :22. Debian trixie does not enable `ssh.socket` on install — checked against the real package rather than assumed — so the service unit is the whole of the run state and `sshaccess.Manager`'s `ssh.service` handling is complete.

**Host keys are generated per box, not baked.** Debian's postinst runs `ssh-keygen -A` at install time, which on an image build means every box provisioned from one image ships the same host keys — anyone holding the published image could impersonate any hosted box to its owner's ssh client. The build deletes them, the same way it leaves `/etc/machine-id` empty. Debian's own `sshd-keygen.service` cannot replace them here: it is `ConditionFirstBoot=yes` and only pulled in by `ssh.service`, and on this profile sshd usually first starts long after the first boot, when that condition is false — so a box that turned SSH on weeks later would get "no hostkeys available" and sshd would never come up. `malmo-sshd-keygen.service` is the same job without the condition, `WantedBy=ssh.service`, so it runs on whichever boot the toggle first starts the daemon. Both halves are asserted: no baked keys at boot, and keys present once a real login has succeeded.

**The appliance gets the two files `BUILD.md` # SSH specifies and no build wrote.** They live in a new `dev/test-qemu/appliance/` tree, checked in at their in-image paths and copied into the generated `mkosi.extra/` by that lane's `bootstrap.sh`. They are product configuration, not build output — on a real box the malmo `.deb` ships them — so they are not generated by the script the way the harness's own scaffolding is.

- `etc/nftables.d/malmo-ssh.conf` default-denies :22 and allows the three private ranges plus `iif lo`, in its own nftables table so loading it never touches Docker's rules. `etc/systemd/system/malmo-ssh-firewall.service` loads it on every boot: a standing policy, not something that follows the daemon, so there is no window in which the port is reachable from off the LAN.
- `etc/ssh/sshd_config.d/malmo-hardening.conf` carries `PermitRootLogin no` and `PasswordAuthentication yes`. Static and separate from the generated drop-in, so the two settings hold while no account is enabled and nothing has been rendered.

**The harness's own way in was decided rather than discovered.** #467's closing note asked whoever picked it up to settle this early. sshd takes the first value it obtains for a keyword and reads `sshd_config.d/*.conf` in filename order, so `malmo-hardening.conf` would have won `PermitRootLogin` over the medium lane's own drop-in and shut the harness out of its own image. The harness drop-in is renamed `00-medium-test.conf` so it sorts first. The second half of the answer is that **the appliance lane does not exercise the account toggle at all**: enabling an account renders an `AllowUsers` naming that account and no other, and `AllowUsers` is not additive across files, so root would stop being considered and the harness would cut its own connection mid-run. Turning the last account off would stop sshd and do the same. The medium lane asserts the shipped posture instead — both files present, the rule live in the kernel, the drop and each allow checked separately — and the daemon lifecycle is proved in the cloud lane, which reaches its box over a serial console and has no connection to lose.

**A new `ssh` boot in the cloud lane, in the publish gate.** It takes its own overlay and box-id, seeded with the test-portal key so it can mint a real owner session. Everything else happens inside the guest: the box makes its own keypair with `ssh-keygen` and connects to itself, so nothing crosses the air gap. In order, it asserts:

1. :22 closed and `ssh.service` inactive at boot, with nothing rendered.
2. Turning SSH on with no key refused (422), and :22 still closed.
3. A key added and SSH turned on: the unit active, :22 listening, the drop-in naming the account in `AllowUsers` and in a `Match` block, the managed key file written.
4. A real `ssh -i key owner@127.0.0.1` succeeding. Then a password-only attempt failing, with sshd's own list of authentications that can continue read off the wire: it says `publickey` and nothing else. That is the server saying no password is accepted here, which no rendered string can tell you.
5. The optional second factor turned on: the drop-in requires `publickey,password`, the same key that just worked no longer gets in, and sshd asks for a password after accepting it. The AND, on a real sshd.
6. Removing the only key while SSH is on refused (422), with the key file still in place.
7. SSH turned off: the unit stopped, :22 closed, the managed key file gone.
8. A second account created, given SSH, then deleted: its name gone from the drop-in, its key file gone from `/etc/ssh/malmo-authorized-keys/`, and :22 closed again. That cleanup landed in #464 and nothing outside a booted box could check it.

The boot is in the non-PR gate list in `ci-cloud-image.yml`, for the same reason `access` and `update` are: an image that boots with sshd running has no control over its own port, and one that cannot stop it again can never close it. Neither failure can be allowed to publish.

**One thing had to be worked around, not fixed.** Every SSH write is elevation-class, elevation re-verifies the account's password through PAM, and a hosted owner's password is generated by the SSO auto-create and thrown away — so no hosted owner can pass the re-auth gate for any elevation-class operation. That is #469, well outside this slice. The scenario sets a password as host root, which is the same write the brain would make through host-agent, and re-elevates before each write so the five-minute window cannot expire mid-scenario under CI's TCG-only QEMU.

## Known gaps & deviations

- **The mesh interface is not in the nftables rule.** `BUILD.md` # SSH says the rule also allows the mesh interface, templated at host-agent startup from whichever mesh client is installed. v1 installs none — the malmo mesh is deferred and remote access is the user's own Tailscale — so there is no interface to name. The file documents the placeholder; the clause lands with the mesh client.
- **The appliance firewall half is not covered by CI.** That lane is local-only, so it needs a run of `sudo -E ./dev/test-qemu/run-medium-tests.sh`; the result is recorded in the PR body.
- **The appliance lane never exercises the account toggle,** for the harness-lockout reason above. So the daemon lifecycle is proved on hosted only. The manager is the same code on both profiles and only the mandatory factor differs, but "the same code" is an argument, not a test.
- **A hosted owner still cannot turn SSH on** (#469). The lane gets past it as host root, which is not a path a user has.
- **Nothing polls `/v1/ssh/state`,** so config drift is still unsurfaced. Carried forward unchanged from #464.
- **The appliance image still bakes host keys.** The build-time `ssh-keygen -A` is undone on hosted only. It does not bite the medium lane, which enables sshd at boot so Debian's own `sshd-keygen.service` fires, but a real appliance image would want the same treatment once malmo owns the daemon's run state there. Out of scope here; named so it is not discovered later.
- **No UI.** Settings has no Device access screen yet, so the whole feature is API-only on both profiles.
